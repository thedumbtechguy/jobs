# Dev Registry — Design

A catalogue of our developers, what they've built, who they know, and where
they can work next. Built on [Plutonium](https://github.com/radioactive-labs/plutonium-core),
SQLite, and deployed self-hosted with Kamal.

This replaces the DevCongress Jobs app. The old app never shipped, so there is
no data to migrate; we carry over its ideas, not its tables.

## Goals

1. **Catalogue every dev.** Each developer has a profile with location, contact
   details, links, skills, experience and availability. Profiles are
   browsable and searchable.
2. **Show the work.** Developers post projects and credit the other developers
   who worked on them.
3. **Link people.** Follow anyone; two people who follow each other are
   *connected*. Connections can endorse each other's skills.
4. **Hire.** Companies post jobs. A job accepts applications in the app,
   through an external link, or both.

## Stack

| Concern | Choice |
|---|---|
| Framework | Rails 8.1 + Plutonium (resources, policies, interactions, portals) |
| Database | SQLite for everything (primary, queue, cache, cable, errors) |
| Background jobs | Solid Queue, with recurring tasks in `config/recurring.yml` |
| Backups | Litestream |
| Auth | Rodauth: a `user` account (signup, optionally Google) and an `admin` account (invite-only, TOTP) |
| UI | Phlex, Tailwind, Stimulus, Turbo (Plutonium defaults), styled after devcongress.org: cream/ink/pink/yellow, DM Serif Display + Inter (self-hosted), pill buttons, ink-bordered cards with a pink offset shadow (`.dc-card`) |
| Search | Behind a `Searchable` concern. `LIKE` for now; swapped for the in-house SQLite search when it lands |
| Deploy | Kamal on our own hosts, with SQLite files on a mounted volume |
| Config | Environment variables only; no Rails credentials |

## Layout

Public pages live in the **main app**. Signed-in work happens in **portals**.
Domain code is grouped into **feature packages**.

```
app/                    main app: User, Admin, Company, CompanyUser, Skill
                        public pages: landing, /devs, /@handle, /projects, /jobs, /companies
packages/
  developers/           Developers::Profile, Developers::Experience, Developers::ProfileSkill
  showcase/             Project, ProjectContributor, ProjectSkill
  network/              Follow, Endorsement
  hiring/               Hiring::JobPost, Hiring::JobApplication
  invites/              CompanyUserInvite (generated by pu:saas:setup)
  dashboard_portal/     /dashboard           (user account)  home: links to your profile and companies
  developer_portal/     /developer/:handle   (user account, scoped to Developers::Profile) profile, experience, skills
  company_portal/       /company/:slug       (user account, scoped to Company) jobs, members, invites, applicants
  admin_portal/         /admin               (admin account) moderation, skills taxonomy
```

### Two kinds of entity

**Developer profiles and companies are both entities.** Each has its own portal,
scoped by URL, and users reach only the ones they own or belong to.

| Entity | Portal | Who can open it | How a user gets one |
|---|---|---|---|
| `Developers::Profile` | `/developer/:handle` | Its owner. One profile per user (`belongs_to :user`) | Onboarding, or `/setup/developer/new` later |
| `Company` | `/company/:slug` | Its members (`CompanyUser`, role `owner` or `recruiter`) | Onboarding, `/setup/company/new`, or an email invite |

- `User`, `Company`, `CompanyUser` and the company portal come from
  `pu:saas:setup`, run **without** its welcome flow, because that flow forces
  everyone to create a company.
- `Skill` lives in the main app because projects and jobs will use it too. It
  is a global taxonomy: `SkillPolicy` skips entity scoping, and only admins
  create skills.
- The package is `developers` and the model is `Developers::Profile`. That
  avoids a "profiles/Profile" package, and avoids clashing with Plutonium's
  `pu:profile` account-settings page.

### Accounts and onboarding

1. A person signs up as a `User`. After login, `/welcome` checks for a
   pending company invite, then sends them to `/dashboard`.
2. Anyone with **neither** a developer profile **nor** a company is sent to
   `/onboarding` first, from any portal (`RequiresOnboarding`, `User#onboarded?`).
3. Onboarding asks what they're here for: **"I'm a developer"** (name, handle,
   headline, location) and/or **"I'm hiring for a company"** (company name,
   website). At least one is required.
4. Submitting creates whichever was chosen, in one transaction
   (`app/forms/onboarding.rb`), and lands them in that portal. If they chose
   both, they land on the dashboard.
5. The dashboard links to both, and offers to create whichever one they skipped.
   Recruiters invited to a company count as onboarded.

## Domain model

```
users ─1:1─ developers_profiles ─< developers_experiences
                │   ├─< developers_profile_skills >─ skills ─< project_skills >─ projects
                │   ├─< project_contributors >───────────────────────────────────┘
                │   ├─< follows (follower_id → followee_id)
                │   ├─< endorsements (endorser_id, profile_skill_id)
                │   └─< job_applications >─ job_posts
users ─< company_users (role) >─ companies ─< job_posts ─< job_renewals
```

### `developers` package

**Developers::Profile** (the catalogue entry, at most one per user)

| Group | Fields |
|---|---|
| Identity | `handle` (unique, used in `/@handle` and `/developer/:handle`), `name`, `headline`, `bio` (markdown), `avatar` (later) |
| Location | `city`, `region`, `country`, `timezone`, `remote_ok`, `open_to_relocation` |
| Contact | `contact_email`, `phone`, `website_url`, `github_url`, `linkedin_url`, `x_url` |
| Status | `availability` (`not_looking`, `open`, `looking`), `seniority`, `years_experience` |
| Privacy | `contact_visibility` (`everyone`, `members`, `connections`), `listed` (appears in the directory) |

- `contact_visibility` will be enforced in the profile policies used by the
  public pages, so hidden contact fields never render.

**Developers::Experience**
- `profile`, `title`, `company_name`, optional `company` (links to a company on
  the site), `location`, `started_on`, `ended_on` (blank for the current role),
  `description`.

**Skill** (main app) and **Developers::ProfileSkill**
- A curated taxonomy that admins manage. `ProfileSkill` joins profiles and
  skills, with `level` (`beginner` to `expert`) and `years`. Each skill appears
  once per profile. Endorsements will point at it.

### `showcase` package

**Project**
- `owner` (a developer profile), `title`, `slug`, `summary`, `body` (markdown),
  `repo_url`, `demo_url`, `started_on`, `ended_on`, `cover_image`.

**ProjectContributor**
- `project`, `profile`, `role`, and `status` (`pending` or `confirmed`).
- The owner invites a contributor and the contributor confirms. Only confirmed
  contributors show publicly, so nobody can claim work with someone who didn't
  agree to it.

**ProjectSkill**
- The stack a project was built with.

### `network` package

**Follow**
- `follower_id` and `followee_id`, both developers, unique on the pair.
- **Connection = mutual follow.** It is not a table. It is a scope:

  ```ruby
  # Developer
  has_many :following, through: :outgoing_follows, source: :followee
  has_many :followers, through: :incoming_follows, source: :follower
  def connections = following.where(id: followers.select(:id))  # both directions exist
  def connected_to?(other) = connections.exists?(other.id)
  ```

  Two indexed lookups, and there is no request/accept state to keep in sync.
  "Accepting" a connection is just following someone back.
- The UI shows **Follow**, **Following**, **Follow back** or **Connected**,
  depending on the two follow rows.

**Endorsement**
- `endorser` (a developer profile) and a `profile_skill`.
- The policy only allows it when the endorser is connected to the skill's
  owner, and nobody can endorse themselves.

### `hiring` package

Ported from the old app, with its rough edges removed.

| Old app | New app |
|---|---|
| `Company` with `clients` linking users | `Company` (`slug`, `name`, `website`, `description`, `city`, `country`) and `CompanyUser` (`role`: `owner` / `recruiter`), both in the main app. Members join through email invites |
| Ownership checks repeated in controllers | `company_portal` is scoped to `Company` through the URL path, so policies only ever see the current company's rows |
| `Job` with `salary` as a numrange | `JobPost`: `title`, `description` (markdown), `employment_type`, `seniority`, `salary_min`, `salary_max`, `salary_currency`, `remote_ok`, `city`, `country`, `apply_url`, `accepts_applications`, `published_at`, `expires_at`, `filled_at`, `archived_at` |
| `renewals` table plus the 30-day window in raw SQL | `JobRenewal` keeps the history. `expires_at` is stored on the job, so `JobPost.active` is `where(archived_at: nil, filled_at: nil).where("expires_at > ?", Time.current)` |
| Actions to mark filled/vacant and renew | Interactions: `PublishJob`, `RenewJob` (only once expired), `MarkFilled`, `MarkVacant`, `ArchiveJob` |
| `scheduler.rake` expiry emails | `JobExpiryReminderJob` and `JobExpiredJob` in `config/recurring.yml`, sending the same four `JobsMailer` emails |
| Tweet on publish | Dropped. Could come back later as an `AnnounceJob` webhook |

**Ways to apply**
- A job must have `apply_url` or `accepts_applications`, and can have both.
  This is a model validation.
- With `apply_url`, the job page shows a button that links out.
- With `accepts_applications`, a signed-in developer runs the `Apply` action,
  which creates a `JobApplication`:
  - `job_post`, `profile`, `cover_note`, optional `resume` attachment.
  - `status`: `submitted`, `reviewing`, `shortlisted`, `rejected`, `hired`, `withdrawn`.
  - Unique on the job/developer pair.
- Company members manage applicants in `company_portal`: a nested
  `job_posts/:id/job_applications` resource with status interactions.
- Applicants see and can withdraw their applications in `dashboard_portal`.

## Portals and access

| Surface | Who | Contents |
|---|---|---|
| Main app (public) | Anyone | Landing page, developer directory with filters (skill, country, availability, remote), `/@handle` page, projects, jobs, company pages. Plain Rails controllers and Phlex views, reading through the same policies |
| `dashboard_portal` | Signed-in user | Home: links to my developer profile and companies, and creates whichever is missing. Later: follows, connections, my applications |
| `developer_portal` | The profile's owner | Profile, experience, skills. Later: projects, contributor invites, endorsements received |
| `company_portal` | Company members | Job posts and their lifecycle actions, applicants, members |
| `admin_portal` | Admin account | Every resource, skills taxonomy, hiding/unlisting developers, projects or jobs |

- **Signup and onboarding:** see *Accounts and onboarding* above.

## Search

Every searchable model includes `Searchable` and declares its fields:

```ruby
class Developer < ApplicationRecord
  include Searchable
  searchable :name, :handle, :headline, :bio, :city, :country
end
```

- `Searchable.search(q)` uses `LIKE` for now.
- When the in-house SQLite search is ready, only the concern changes.
- Plutonium definitions call `search { |scope, q| scope.search(q) }`, and the
  public pages call the same method.

## Deploy

- Kamal, using `config/deploy.yml` from `rails new`.
- One web role, with Solid Queue in-process (`SOLID_QUEUE_IN_PUMA`).
- `storage/` is on a persistent volume, and Litestream replicates the SQLite
  files to S3-compatible storage.

## Build order

1. **Skeleton** ✅: Plutonium + SQLite stack, `user` and `admin` Rodauth
   accounts, companies and invites, portals mounted, CI (tests plus
   standardrb), Kamal config.
2. **Catalogue:** `developers` package with profile, experience and skills ✅,
   developer portal ✅, onboarding ✅, public directory (`/devs`) and `/@handle` ✅.
3. **Showcase:** projects and the contributor confirm flow.
4. **Hiring:** companies and the company portal ✅, `hiring` package with job
   posts, lifecycle actions (publish, renew, filled, reopen, archive) and
   applications ✅, developers browse and apply from the developer portal ✅.
   Public `/jobs`, job and company pages ✅. A new company's first job is
   reviewed by an admin (emailed) before it goes live; approval trusts the
   company ✅. Still to do: expiry reminder emails, active-job cap per company.
5. **Network:** follows and connections, endorsements, and "people you may
   know" (connections of connections).
6. **Polish:** landing page and admin moderation, then plug in the SQLite
   search.

## Visibility

| Record | Settings | Default |
|---|---|---|
| Developer profile | Public (directory, `/@handle`, search engines) · Members only · Hidden (owner only) | Members only |
| Contact email/phone | Everyone who can see the profile · Members only · Only you (until connections exist) | Members only |
| Job post | Public · Members only. Drafts, jobs in review, expired, filled and archived jobs are never shown | Public |

Guests see public records; signed-in members also see members-only ones. Pages
for non-public records are marked `noindex`.
